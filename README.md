# Goose CIF structure-factor PoC

Gooseで複数のCIFを読み、ファイル単位のワーカープールで構造因子を並列計算するPoCです。Rust、CPythonのスカラー実装、NumPyのバッチ実装を同じ条件で比較します。

## 計算モデル

倍精度で `F(h,k,l) = Σ occupancy_j Z_j exp(2πi(h x_j + k y_j + l z_j))` を直接計算します。反射範囲は各軸 `-hmax ... +hmax`、000も含みます。標準出力は各ファイルの `Σ |F|²`。Gooseでは `SF_WRITE=1` を指定すると、入力の隣に `.sf.csv` を付けたファイルへ `h,k,l,re,im,intensity` を保存します。

これは**原子散乱因子を原子番号Zで近似する性能評価用モデル**です。散乱角依存のX線原子散乱因子、異常散乱、温度因子、消衰などは未実装で、精密な回折強度予測には使えません。FFTや結晶の周期性による計算省略は使わず、全実装で同じ直接和を行います。

一般の小分子・無機結晶CIFはGemmiで読み、空間群の対称操作を展開し、特殊位置を原子サイトごとに重複排除します。正規化後のCIFには分率座標と独自タグ `_poc_effective_electrons`（occupancy × Z）を格納します。各言語が直接読むのはこの限定形式です。一般CIFパーサ自体の比較ではありません。複数data block・高分子mmCIF・磁気対称性は対象外です。

## セットアップと実行

Linux、Python 3、git、GCC/G++、Rust（rustupで導入）を用意して実行します。セットアップはPython依存をvenvへ、Gooseを `.tools/` へ配置し、Gooseのコミットを固定してビルドします。測定対象はTinyCC実行ではなくGCC -O2でビルドしたネイティブ実行ファイルです。Rustも `-C opt-level=2` です。

```bash
bash scripts/setup.sh
source .venv/bin/activate
python scripts/generate_known.py
python scripts/check.py
python scripts/bench.py 8 3
# workers=4, hmax=8, 入力ファイル群
src/sf 4 8 data/*.cif
SF_WRITE=1 src/sf 4 8 data/*.cif
```

自分のCIFを使う場合は別ディレクトリへ正規化します（空間群名と元素情報が必要）。

```bash
python scripts/prepare.py --out normalized sample1.cif sample2.cif
src/sf 4 12 normalized/*.cif
```

## 入力CIF

`fixtures/` に以下の理想的な従来単位胞を生成します。外部データのダウンロードではなく、教科書的な既知の分率座標から生成した理想結晶です。格子定数は代表値で、温度・実験条件を特定する測定データではありません。P1として単位胞内の全原子を明示しています。

| 構造 | 格子定数 Å | 原子数/単位胞 | 5³スーパーセル | 6³スーパーセル |
|---|---:|---:|---:|---:|
| NaCl（岩塩） | 5.6402 | 8 | 1000 | 1728 |
| ダイヤモンド | 3.567 | 8 | 1000 | 1728 |
| CsCl | 4.123 | 2 | 250 | 432 |
| SrTiO₃（立方晶ペロブスカイト） | 3.905 | 5 | 625 | 1080 |

`generate_known.py` が元のCIFをGemmiで読み、5×5×5と6×6×6へ複製します。比較入力は8ファイル、合計7843原子。hmax=8では各ファイル4913反射、合計38,532,659原子・反射ペアを評価します。スーパーセルのhklは元の単位胞のhklとは異なります。

## ベンチマーク結果

2026-10-27、AMD EPYC 9V74の仮想環境（CPU割当4コア分）、CPython 3.12.14で実測。Gooseの固定コミット、ライブラリ版、コンパイラ設定は環境JSONに記録しています。

| Language | Workers | Wall s | CPU s | CPU % | Tree RSS MiB |
|---|---:|---:|---:|---:|---:|
| goose | 1 | 0.900 | 0.898 | 99.750 | 1.320 |
| rust | 1 | 0.694 | 0.687 | 99.275 | 1.523 |
| python | 1 | 6.391 | 6.393 | 100.014 | 23.051 |
| numpy | 1 | 1.003 | 1.008 | 100.236 | 45.074 |
| goose | 4 | 0.334 | 0.928 | 277.814 | 1.988 |
| rust | 4 | 0.274 | 0.732 | 276.089 | 1.883 |
| python | 4 | 2.532 | 7.270 | 288.646 | 53.332 |
| numpy | 4 | 0.416 | 1.020 | 245.020 | 107.074 |

4ワーカーではGooseはスカラーPythonの約7.6倍、NumPy版の約1.24倍の速度でした。一方、Rustより約22%遅く、CPU時間も約27%多く消費しました。RSSもRustより約0.1 MiB大きく、この条件ではRustに対するメモリ優位は確認できません。Python/NumPyのRSS合計はGooseより大きいですが、プロセス方式・共有ページ重複計上も影響します。

Gooseの1→4ワーカーの速度向上は約2.69倍。ファイルごとの原子数が異なるため負荷の偏りもあります。Gooseが常にRustより速い／省メモリという結論にはなりません。


## 測定方法と検証

- 各条件でウォームアップ1回、その後3回測定し、各指標の中央値を記録します。ファイル読み込み、ワーカー起動・終了、チェックサム出力を含み、コンパイルとGemmiによる正規化は除外します。OSページキャッシュは温まった状態です。CSV出力は無効です。
- GooseとRustはスレッド、PythonとNumPyはGILを避けるプロセスプール。NumPyは128反射ずつバッチ処理し、BLAS/OMPを1スレッドに制限します。
- Wallは経過時間、CPUはLinux wait4によるユーザー＋システムCPU秒（終了・回収された子プロセスを含む）。CPU % = CPU秒/経過秒 × 100で、4コアなら最大約400%です。
- Tree RSSは2ms間隔でプロセスツリーのRSSを合計したピーク値です。仮想アドレス予約量ではありません。共有ページの重複計上があり、瞬間的なピークも取り逃がすため、厳密な物理メモリ使用量ではありません。exec前の測定用PythonプロセスのRSSは除外します。
- 2原子のF000、系統消滅、Gooseの各反射の複素数CSVを解析解と比較。CIFの対称展開・特殊位置・占有率も検証します。ベンチマークでは全ファイルのチェックサムを全実装・並列数で比較します（相対許容誤差1e-9）。
- 原子数・反射数が少ない、理想結晶である、sin/cosの実装やコンパイラが異なる、といった条件で結果は変わります。言語全般の性能の順位を示すものではありません。サブミリ秒級の差やRSSの小差の解釈には注意が必要です。
